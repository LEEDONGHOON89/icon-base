## 주의사항

- `parser_rules.config_json` — JSONB 타입: 파서 타입별 키가 다름
  - DELIMITER: `delimiter`(필수), `index`(기본 0)
  - FIXED_WIDTH: `startByte`(필수), `byteLength`(기본 전체)
  - REGEX: `pattern`(필수), `group`(기본 0)
- 파서 삭제 시 `data_source_schemas.parser_id`는 SET NULL로 자동 해제
- 파서 타입은 생성 후 변경 불가 (PUT 요청에서 parserType 필드 없음)
- 1개 원본 필드 → N개 추출 필드: 엔진에서 원본 필드는 mappedRow에 넣지 않고 추출 결과만 저장

## [재설계] V1_0_4 — 파서 데이터소스 레벨 재설계 (2026-04-20)

### 변경 배경
- 초기 설계: `data_source_schemas` 개별 필드에 파서 연결 (1:1)
- 재설계: 데이터소스 단위로 파서 연결 (1:N), `source_field`를 파서에 지정

### DB 변경 — V1_0_4

**파일**: `db/migrations/V1_0_4__parser_redesign.sql`

| 변경 | 내용 |
|---|---|
| `parsers.source_field` 추가 | 파싱 대상 원본 필드명 (예: `line`) |
| `parsers.config_json` 추가 | 파서 레벨 설정 (DELIMITER: `{"delimiter":"|"}`) |
| `parser_rules.config_json` nullable 변경 | DELIMITER는 파서 레벨 설정 사용, FIXED_WIDTH/REGEX만 규칙별 사용 |
| `data_source_schemas.parser_id` 삭제 | 데이터소스 레벨로 이동 |
| `data_source_parsers` 신규 | 데이터소스:파서 = 1:N, `parser_order`로 실행 순서 지정 |

### 파서 타입별 설정 구조 (재설계)

**구분자 파서 (DELIMITER)**
```
parsers:      { source_field: "line", config_json: {"delimiter":"|"} }
parser_rules: [{ rule_order:0, config_json:null, target_field_name:"COLUMN1" }, ...]
```

**고정폭 파서 (FIXED_WIDTH)**
```
parsers:      { source_field: "line", config_json: null }
parser_rules: [{ rule_order:0, config_json:{"byteLength":4}, target_field_name:"COLUMN1" }, ...]
              startByte는 엔진에서 rule_order 기준 자동 누적 계산
```

**정규식 파서 (REGEX)**
```
parsers:      { source_field: "line", config_json: null }
parser_rules: [{ rule_order:0, config_json:{"pattern":"^(\\w+)","group":1}, target_field_name:"COLUMN1" }, ...]
```

### 데이터 흐름
```
landing_records { line: "A|B|C", ip: "1.2.3.4" }
  → data_source_parsers 에서 파서 목록 조회 (parser_order 순)
  → 파서 적용: source_field="line" 파싱 → COLUMN1='A', COLUMN2='B', COLUMN3='C'
  → 원본 "line" 필드 제거
  → 결과: { COLUMN1:'A', COLUMN2:'B', COLUMN3:'C', ip:'1.2.3.4' }
  → data_source_schemas 매핑 (COLUMN1→표준필드 등)
  → mapped_storages 저장
```
