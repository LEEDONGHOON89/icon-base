# 직원 본인계좌 이상거래 통합 시나리오

## 개요
**고객 계좌**에서 **직원 본인 계좌**로 이체 시 즉시 탐지합니다.

**탐지 목표**: S_EMP_SELF_AC (직원 본인계좌 이상거래)

**탐지 플로우**: Event Stream → Derived Field → Aggregate (where_json 필터링) → Scenario

**핵심 차이점**:
- `S_CORP_TO_EMP` (법인→직원): 법인 계좌(100-xxx-xxx) → 직원 계좌
- `S_EMP_SELF_AC` (본 시나리오): **고객 계좌**(xxx-xxx-xxx) → 직원 본인 계좌

---

## 실행 순서 (총 10건)
1. DS_EMPLOYEE - 직원 HR 등록 (3건)
2. DS_EMP_ACC - 직원 계좌 등록 (3건)
3. DS_CUST_ACC - 고객 계좌 등록 (2건)
4. DS_XFER_APPR - 이체 거래 (2건)

## 단계별 상세 설명

### 1단계: 직원 HR 등록 (DS_EMPLOYEE)

**예상**: EMPLOYEE 엔티티 3개 생성

### 2단계: 직원 계좌 등록 (DS_EMP_ACC)

**예상**:
- EMPLOYEE 엔티티 속성 보강
- EMPLOYEE-OWNS→ACCOUNT 6건 (EMP001: 3개, EMP002: 2개, EMP003: 1개)

### 3단계: 고객 계좌 등록 (DS_CUST_ACC)

**예상**:
- CUSTOMER 엔티티 2개 생성

**파생 필드**:
- `is_customer_sender`: sender_account가 CUSTOMER 소유 계좌인지 (고객 계좌)

**예상**:

## 검증 SQL

### 1. 직원 엔티티 확인
```sql
SELECT entity_type, entity_id, attributes->>'emp_name', attributes->>'dept_name'
FROM entity_attributes
WHERE entity_type = 'EMPLOYEE'
ORDER BY entity_id;
```

**예상**: EMP001, EMP002, EMP003 생성

### 2. 직원-계좌 관계 확인
```sql
SELECT entity_id, attributes->'owned_accounts', attributes->'family_accounts'
FROM entity_attributes
WHERE entity_type = 'EMPLOYEE'
ORDER BY entity_id;
```

**예상**: EMP001(3개 owned, 2개 family), EMP002(2개 owned, 1개 family), EMP003(1개 owned, 0개 family)

### 3. 고객-계좌 관계 확인
```sql
SELECT entity_id, attributes->'owned_accounts'
FROM entity_attributes
WHERE entity_type = 'CUSTOMER'
ORDER BY entity_id;
```

**예상**: CUST_100, CUST_101 각 1개 계좌

### 4. 이벤트 스트림 확인
```sql
SELECT
  event_stream_id,
  event_data->>'transaction_id' as tx_id,
  event_data->>'approver_id' as approver_id,
  event_data->>'sender_account' as sender_account,
  event_data->>'receiver_account' as receiver_account,
  event_data->>'is_customer_sender' as is_customer_sender,
  event_data->>'is_employee_receiver' as is_employee_receiver
FROM event_stream
WHERE data_source_id = 'DS_XFER_APPR'
ORDER BY event_dt;
```

**예상**: 2건 모두 is_customer_sender=true AND is_employee_receiver=true (XFER_EMP_SELF_001, 002)

### 5. 집계 결과 확인
```sql
SELECT
  aggregate_id,
  group_key,
  matched_count,
  threshold_count,
  pass,
  detected_at
FROM detect_aggregates
WHERE aggregate_id = 'AGG_EMP_SELF_AC_CNT'
ORDER BY group_key;
```

**예상**:
- group_key=EMP001: matched_count=2, threshold_count=1, pass=true (탐지)

### 6. 시나리오 탐지 확인
```sql
SELECT
  scenario_id,
  group_key,
  detected_at
FROM detect_scenarios
WHERE scenario_id = 'S_EMP_SELF_AC'
ORDER BY detected_at;
```

**예상**: S_EMP_SELF_AC 2건 탐지
- group_key: EMP001 (2건 집계)

## 탐지 흐름

```
고객 계좌 → 직원 본인 계좌 이체 발생
              ↓
1. Event Stream 생성
   - sender_account: 100-111-222333 (CUSTOMER 소유)
   - receiver_account: 1001-234-567890 (EMPLOYEE 소유)
   - approver_id: EMP001
              ↓
2. Derived Rules 실행
   - is_customer_sender: true (고객 계좌 확인)
   - is_employee_receiver: true (직원 본인 계좌 확인)
              ↓
3. AGG_EMP_SELF_AC_CNT 집계
   - where_json으로 2개 조건 AND 필터링
   - group_key: approver_id (EMP001)
   - threshold_count=1 → 즉시 탐지!
              ↓
4. S_EMP_SELF_AC 시나리오 탐지
   - risk_level: HIGH
   - 고객 자금 착복 가능성
```

### 탐지 패턴

```
케이스 1: EMP001 - 첫 번째 탐지
└─ 10:00: CUST_100(100-111-222333) → EMP001 본인(1001-234-567890) 5,000,000원 → 🚨 탐지!

케이스 2: EMP001 - 두 번째 탐지
└─ 14:00: CUST_101(200-222-333444) → EMP001 본인(1001-234-567891) 3,000,000원 → 🚨 탐지!
```

## 탐지 목적

직원이 업무상 접근 가능한 **고객 자금을 본인 계좌로 빼돌리는** 횡령/착복 행위를 탐지합니다.

**탐지 조건**:
1. 출금계좌가 고객 소유 (`is_customer_sender = true`)
2. 입금계좌가 직원(approver_id) 본인 소유 (`is_employee_receiver = true`)
3. 발생 즉시 탐지 (`threshold_count = 1`)

**핵심**:
- 고객 계좌 → 직원 본인 계좌 이체는 **비정상**
- S_CORP_TO_EMP (법인→직원)와는 **별개 시나리오**
- 계좌 번호 패턴: 고객(xxx-xxx-xxx), 직원(1xxx-xxx-xxx), 법인(100-xxx-xxx) 구분
