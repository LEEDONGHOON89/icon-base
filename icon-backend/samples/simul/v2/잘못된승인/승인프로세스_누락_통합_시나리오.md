# 승인 누락 이체 통합 시나리오

## 개요
이체 거래가 발생했으나 승인 기록이 없는 경우를 탐지합니다.

**탐지 목표**: SCN_NO_APPR (승인 누락 이체)

**탐지 플로우**: Event Stream → Aggregate (where_json 필터링, SINGLE_ROW) → Scenario

**특징**: Rule 없이 where_json으로 직접 필터링, SINGLE_ROW 모드로 즉시 탐지

---

## 실행 순서 (총 2건)
1. DS_EMPLOYEE - 직원 HR 등록 (1건)
2. DS_XFER_APPR - 이체 거래 (1건)

## 시나리오 설명

정상적인 이체 거래는 반드시 승인 절차를 거쳐야 하나, 승인 기록(approval_datetime)이 없는 경우 내부 통제 우회 가능성이 있습니다.

- **정상 케이스**: 이체 + 승인 일시 기록 존재
- **탐지 케이스**: 이체 + 승인 일시 없음 (approval_datetime=null)
- **핵심 필드**:
  - `approval_datetime`: 승인 일시 (null이면 승인 없음)
  - `approver_id`: 승인자 (null이면 승인자 없음)

## 탐지 목적

### 승인 누락 이체 (SCN_NO_APPR)
승인이 필요한 거래임에도 **승인자 정보나 승인 시간이 누락**된 비정상 거래를 탐지합니다.

**탐지 조건**:
1. `approval_datetime IS NULL` (승인 시간 없음)
2. `approver_id IS NULL` (승인자 미지정)
3. SINGLE_ROW 모드로 단일 이벤트 즉시 평가
4. 1건만 있어도 즉시 탐지 (`threshold_count=1`)

**위험성**:
- **승인 프로세스 우회**: 정상적인 승인 절차를 거치지 않음
- **내부통제 실패**: 권한 분리 원칙 위반
- **권한 없는 거래 실행**: 승인자 없이 임의 거래 가능
- **부정 거래 가능성**: 의도적인 승인 우회

**정상 프로세스**:
- 정상: 이체 요청 → 승인자 검토 → 승인 완료 → approval_datetime 기록
- 비정상: 이체 요청 → 승인 없이 실행 → approval_datetime = null

## 💡 핵심 포인트

### 1. where_json 직접 필터링의 장점

#### ❌ 복잡한 방식 (Rule 사용)
```
1. Rule 등록 (RULE_NO_APPROVAL)
   - where_json: {"approval_datetime": null}
    ↓
2. Aggregate 등록 (AGG_NO_APPROVAL_CNT)
   - predicate_rule_id: RULE_NO_APPROVAL
    ↓
3. 이벤트 발생 시
   - detect_rules 테이블에 룰 매칭 결과 저장 (불필요한 데이터 쌓임)
   - detect_aggregates 테이블에 집계 결과 저장
```

#### ✅ 단순한 방식 (where_json 사용)
```
1. Aggregate 등록만 (AGG_NO_APPROVAL_CNT)
   - where_json: {"approval_datetime": null}
   - predicate_rule_id: NULL
    ↓
2. 이벤트 발생 시
   - detect_rules 테이블 저장 없음 ✨
   - detect_aggregates 테이블에 집계 결과만 저장
```

**장점**:
1. **Rule 테이블 불필요**: rules 테이블 등록 생략
2. **detect_rules 저장 없음**: 불필요한 중간 데이터 축적 방지
3. **설정 간소화**: Aggregate 하나만 등록하면 끝
4. **성능 향상**: Rule 평가 단계 생략
5. **명확한 로직**: 필터 조건이 Aggregate에 직접 명시됨

### 2. SINGLE_ROW 모드
- **단일 이벤트만 즉시 평가** (시간 윈도우 불필요)
- window_minutes=NULL (윈도우 개념 없음)
- 이벤트 발생 즉시 조건 체크 → 즉시 탐지

### 3. where_json 형식 예시

```json
// 간단한 형식 (권장)
{"approval_datetime": null}

// 단일 조건 형식
{"fieldName": "amount", "operator": "GREATER_THAN", "value": 100000}

// 배열 형식 (AND 조건)
[
  {"fieldName": "approval_datetime", "operator": "IS_NULL"},
  {"fieldName": "amount", "operator": "GREATER_THAN", "value": 50000000}
]
```

## 💡 왜 Rule이 필요 없는가?

AggregateProcessor.java의 `filterByPredicate` 메서드:
```java
private List<EngineEventStreamEntity> filterByPredicate(String ruleId, List<EngineEventStreamEntity> events, AggregateEntity definition) {
    if (ruleId == null || ruleId.isBlank()) {
        // predicate_rule_id가 없으면 where_json 체크
        String whereJson = definition.getWhereJson();
        if (whereJson != null && !whereJson.isBlank()) {
            log.info("✅ where_json으로 필터링 ({}건)", events.size());
            return filterByWhereJson(events, whereJson);  // ← where_json 직접 평가!
        }
        log.info("✅ 필터링 없이 모든 이벤트 사용");
        return events;
    }
    // ... Rule 기반 필터링
}
```

**predicate_rule_id가 NULL**이고 **where_json이 있으면** → **where_json으로 직접 필터링**됩니다.

## 🎯 핵심 정리

1. **SINGLE_ROW 모드**: 단일 이벤트만 즉시 평가 (시간 윈도우 불필요)
2. **Rule 없이 작동**: `predicate_rule_id`가 NULL이므로 별도의 룰 등록 없이 where_json만으로 필터링
3. **간단한 조건**: approval_datetime=null 체크만으로 탐지
4. **detect_rules 저장 없음**: Rule 평가 단계를 거치지 않아 중간 데이터 축적 방지
5. **즉시 탐지**: 승인 누락 이체 발생 시 즉각 탐지 가능
